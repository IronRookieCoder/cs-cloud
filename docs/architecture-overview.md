# CSC 系统分层架构说明

> 为业务部门提供的非技术性架构概览，解释 csc-bridge 的核心 localserver 在整个系统中的定位与职责。

---

## 一、整体架构（核心三层）

```
┌─────────────────────────────────────────────────────────────┐
│                    用户终端层（前端）                         │
│  • 浏览器（Web 应用）                                        │
│  • 桌面客户端                                                │
│  • IDE 插件                                                 │
└──────────────────────┬──────────────────────────────────────┘
                       │ HTTP / SSE
                       │ (localhost)
                       ▼
┌─────────────────────────────────────────────────────────────┐
│           csc-bridge / localserver（核心服务）               │
│                                                             │
│   ┌─────────────────────────────────────────────────────┐   │
│   │           Runtime 接口（本地能力）                  │   │
│   │   文件 · 终端 · Git · 搜索 · 系统状态              │   │
│   └─────────────────────────────────────────────────────┘   │
│   ┌─────────────────────────────────────────────────────┐   │
│   │           Agent 路由（智能分发）                    │   │
│   │   对话管理 · 权限路由 · 模型切换 · 事件广播         │   │
│   └────────────────────┬────────────────────────────────┘   │
└────────────────────────┼────────────────────────────────────┘
                         │ stdin/stdout
                         │ (JSON-RPC / ACP)
                         ▼
┌─────────────────────────────────────────────────────────────┐
│                  csc-cli（AI 智能体）                        │
│  • 独立的 AI 进程（如 Claude Code、Qwen 等）               │
│  • 负责实际对话、代码生成、工具调用                          │
└─────────────────────────────────────────────────────────────┘
```

**核心设计**：csc-bridge 通过 **localserver**（一个监听在 `127.0.0.1` 的 HTTP 服务）统一对外暴露所有能力，前端、AI 进程都通过这个本地 HTTP 接口交互。

---

## 二、三层定位与职责

### 第一层：用户终端层（前端）

**职责**：用户交互界面

- 展示对话界面、终端、文件浏览器
- 收集用户输入（prompt、文件操作请求）
- 渲染 AI 响应（文本、代码、diff）
- **不直接**与 AI 对话，所有请求都通过 HTTP 发给本地 localserver

**典型形式**：
- 浏览器中的 Web 应用
- 桌面客户端（Electron、Tauri 等）
- IDE 插件（VSCode 扩展等）

**对接方式**：直接调用 `http://127.0.0.1:{port}/api/v1/*`。

---

### 第二层：csc-bridge / localserver（核心服务）

**职责**：本地"智能网关 + 能力中心"，由 **localserver** 这一个 HTTP 服务承担双重身份。

#### 身份一：运行时服务提供者（Runtime 接口）

csc-bridge 自己能做的事（不依赖 AI），通过 `/api/v1/runtime/*` 暴露：

| 能力 | 说明 | 业务场景 |
|------|------|----------|
| 文件操作 | 读取文件列表、获取文件内容 | 用户浏览项目结构 |
| 搜索 | 全文搜索、文件名查找 | 快速定位代码 |
| 版本控制 | Git 状态、分支切换、提交记录 | 代码管理 |
| 终端 | 创建 PTY 会话、执行 shell 命令 | 运行测试、构建 |
| 设备状态 | 健康检查、资源监控 | 系统运维 |

#### 身份二：智能路由器（Agent 路由）

csc-bridge 管理多个 AI 智能体，通过 `/api/v1/agents/*`、`/api/v1/conversations/*` 等暴露：

| 职责 | 说明 |
|------|------|
| **AI 生命周期** | 启动、停止、重启 csc-cli 进程 |
| **对话管理** | 创建会话、发送消息、中断生成 |
| **权限路由** | 将用户的权限批准/拒绝转发给对应 AI |
| **模型切换** | 在不同 AI 模型间切换（如从 Claude 切到 Qwen） |
| **事件广播** | 将 AI 的实时响应通过 SSE 推送给前端 |
| **多路复用** | 同时支持多个对话、多个 AI 并行运行 |

**为什么需要"路由"？**

一个用户可能同时：
- 在对话 A 中使用 Claude Code 编写代码
- 在对话 B 中使用 Qwen 生成文档
- 在对话 C 中使用 Goose 进行代码审查

localserver 确保每个对话的消息路由到正确的 AI 进程。

---

### 第三层：csc-cli（AI 智能体）

**职责**：实际的 AI 推理与执行

- **独立进程**：每个 AI（Claude、Qwen 等）运行在独立的子进程中
- **对话能力**：理解用户问题、生成代码、解释逻辑
- **工具调用**：通过 localserver 的运行时能力执行文件操作、运行终端命令
- **权限请求**：当需要执行敏感操作（写文件、执行命令）时，向用户请求批准

**与 localserver 的通信**：

- 使用标准协议（ACP）通过 stdin/stdout 与 localserver 通信
- localserver 负责启动进程、传递消息、管理生命周期

**为什么独立进程？**

- **隔离性**：AI 崩溃不影响 localserver 主服务
- **灵活性**：可以动态切换不同的 AI（Claude、Qwen、本地模型等）
- **资源控制**：可以限制每个 AI 的内存、CPU 使用

## 三、数据流示意

### 场景：用户让 AI 帮忙写一个函数

```
1. 用户在前端输入："帮我写一个快速排序函数"
   ↓
2. 前端发送 POST http://127.0.0.1:{port}/api/v1/conversations/{id}/prompt
   ↓
3. localserver 接收请求，识别该对话使用的 AI（如 Claude）
   ↓
4. localserver 将消息通过 stdin 转发给对应的 csc-cli 进程
   ↓
5. csc-cli 分析问题，决定需要：
   - 读取项目现有代码（调用 localserver 的文件 API）
   - 生成新函数（AI 推理）
   ↓
6. csc-cli 需要写文件时，发送权限请求给 localserver
   ↓
7. localserver 通过 SSE 推送 permission.asked 事件给前端
   ↓
8. 用户在前端点击"允许"
   ↓
9. 前端发送 POST /api/v1/interactions/permissions/{id}/respond
   ↓
10. localserver 将批准结果转发给 csc-cli
   ↓
11. csc-cli 执行写文件操作（通过 localserver 的运行时 API）
   ↓
12. csc-cli 将生成的函数文本流式返回给 localserver
   ↓
13. localserver 通过 SSE 实时推送给前端显示
```

### 关键点

- **所有前端请求都发给 localserver**，前端不需要知道背后是哪个 AI
- **csc-cli 通过 localserver 提供的运行时 API 操作本地资源**，不是直接访问文件系统
- **权限请求需要用户实时确认**，localserver 负责在 AI 和用户间传递权限消息

## 四、为什么需要 localserver？（业务价值）

### 1. 统一接入层

**问题**：不同的 AI（Claude、Qwen、本地模型）有不同的协议、启动方式、认证机制。

**解决**：localserver 提供统一的 HTTP API 表面，前端只需要对接一个服务，后端可以随意切换 AI。

### 2. 多 AI 并行

**问题**：用户可能同时需要多个 AI 协作（一个写代码、一个写文档、一个做测试）。

**解决**：localserver 管理多个 AI 进程，确保每个对话的消息路由到正确的 AI。

### 3. 安全隔离

**问题**：AI 可能执行危险操作（删除文件、执行恶意命令）。

**解决**：
- localserver 截获所有文件操作、命令执行请求
- 要求用户实时确认（权限审批）
- AI 进程与系统资源隔离（独立进程、沙箱）

### 4. 本地优先

**问题**：代码、文件等敏感数据不应该出域。

**解决**：
- localserver 运行在用户设备上（监听 127.0.0.1）
- AI 推理可以在本地模型执行（无数据出域）
- 只有用户主动选择云端 AI 时才联网

### 5. 标准化对接

**问题**：前端形态多样（Web、桌面、IDE 插件），重复实现对接逻辑成本高。

**解决**：所有形态的前端只需要对接一套 HTTP + SSE 接口，降低集成成本。

## 五、核心概念澄清

| 概念 | 说明 | 类比 |
|------|------|------|
| localserver | csc-bridge 的核心 HTTP 服务 | 操作系统的内核，负责调度和资源管理 |
| csc-cli | AI 智能体进程 | 具体的应用程序（浏览器、编辑器） |
| 对话（Conversation） | 一次完整的 AI 交互会话 | 一个浏览器标签页 |
| Session Mode | 对话模式（build/plan/general） | 应用程序的不同模式（编辑模式/预览模式） |
| Agent Runtime | AI 运行时（Claude/Qwen/Goose） | 不同品牌的应用程序 |

## 六、常见问题

**Q：为什么不直接让前端与 AI 通信？**

A：AI 进程管理、权限控制、多路复用、文件访问控制等逻辑都需要一个中间层。如果前端直接对接 AI，每个前端都需要重复实现这些能力，且无法做统一的安全管控。

**Q：localserver 可以独立工作吗？**

A：可以。localserver 提供完整的运行时 API（文件、终端、Git），前端可以只使用这些能力而不启动 AI。

**Q：如何切换不同的 AI？**

A：通过创建对话时指定 `backend` 参数（如 `claude`、`qwen`）。localserver 会自动启动对应的 csc-cli 进程。

**Q：未来需要远程访问怎么办？**

A：当前架构以本地为主（监听 127.0.0.1）。后续如需远程访问，可在 localserver 之上加一层隧道/网关，无需改动核心逻辑（属于后续演进项，本文暂不涉及）。

## 七、接口清单（供技术团队对接）

### localserver 暴露的接口

所有接口前缀 `/api/v1`，监听 `http://127.0.0.1:{port}`。

| 分类 | 路径前缀 | 说明 |
|------|----------|------|
| 运行时接口 | `/runtime/*` | 文件、终端、Git、搜索等本地能力 |
| AI 管理 | `/agents/*` | AI 列表、健康检查、模型切换 |
| 对话接口 | `/conversations/*` | 创建对话、发送消息、获取历史 |
| 交互接口 | `/interactions/*` | 权限审批、问题回复 |
| 事件流 | `/events/stream` | SSE 实时事件推送 |

**对接示例**：

```
健康检查：GET  /api/v1/runtime/health
创建对话：POST /api/v1/conversations       (Header: X-Backend: claude)
发送消息：POST /api/v1/conversations/{id}/prompt
获取历史：GET  /api/v1/conversations/{id}/messages
权限响应：POST /api/v1/interactions/permissions/{id}/respond
事件订阅：GET  /api/v1/events/stream        (SSE 长连接)
```
