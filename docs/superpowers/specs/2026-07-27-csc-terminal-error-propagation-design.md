# CSC 终态错误向 Multica 工作流节点传递

## Problem Statement

当 Multica 通过 cs-cloud 调度 CSC 执行工作流节点时，CSC 即使已经报告终态错误，节点仍可能显示为完成。用户会因此误以为工作已成功交付，后续节点也可能基于不存在或不完整的结果继续运行。

当前链路中，CSC 已经通过 session 事件报告执行结果和错误，但 cs-cloud 只等待 session 从 `busy` 进入 `idle`，没有把终态结果中的失败语义转换成执行错误。于是 workflow driver 继续向 Multica 调用 task 完成接口。Multica 收到完成回调后，会按正常完成路径推进节点。

此外，Multica 后端已经区分 `failed` 和 `blocked`，但当前执行视图把两者都显示为“阻塞”，导致用户无法从节点状态判断它是等待人工介入，还是已经执行失败。即使 task 保存了错误信息，节点详情也不一定能显示该错误，因为现有错误摘要主要从正常的 worker 或审核者输出中提取。

## Solution

用户在 Multica 中应当看到与 CSC 实际终态一致的节点结果：

- CSC 最终成功时，task 和节点继续走完成路径。
- CSC 内部正在重试时，节点保持运行中，不提前失败。
- CSC 最终报告错误时，cs-cloud 向 Multica 上报 task 失败，关联节点进入 `failed`。
- 用户主动取消时，执行按取消处理，不归类为普通执行错误。
- Multica 将 `failed` 显示为“失败”，并与可恢复、可人工接管的 `blocked` 明确区分。
- 节点详情展示 CSC 提供的用户可读错误消息。

整个方案复用现有 CSC session 事件、Multica task 失败接口和工作流失败状态机，不增加新的节点错误状态，也不把错误文本伪装成正常 worker 输出。

## User Stories

1. 作为工作流发起人，我希望 CSC 终态报错后节点显示失败，以便我不会把失败执行误认为已完成。
2. 作为工作流发起人，我希望失败节点停止正常完成传播，以便下游节点不会依赖无效结果继续执行。
3. 作为工作流发起人，我希望节点详情显示 CSC 的错误消息，以便我能够判断失败原因。
4. 作为工作流发起人，我希望额度不足、最大轮数、模型错误和执行异常等终态错误都能正确传递，以便不同错误场景具有一致行为。
5. 作为工作流发起人，我希望 CSC 的临时 API 重试不会立刻把节点标记为失败，以便可恢复错误能够在 CSC 内部自动恢复。
6. 作为工作流发起人，我希望 CSC 重试后成功时节点仍然显示完成，以便中间波动不会产生错误终态。
7. 作为工作流发起人，我希望单个工具调用失败但数智人随后恢复时，节点不会被提前判定失败，以便工具级错误与 session 终态保持区分。
8. 作为工作流发起人，我希望用户主动取消与执行错误分开显示，以便我能区分人为中止和系统失败。
9. 作为工作流发起人，我希望失败节点保留手动重试入口，以便修复外部条件后可以重新执行。
10. 作为工作流发起人，我希望确定性的数智人错误不会被 Multica 自动反复重试，以免持续消耗额度和运行时资源。
11. 作为工作流审核者，我希望 worker 阶段失败时节点不会进入等待审核状态，以免审核不存在的交付结果。
12. 作为工作流审核者，我希望审核者阶段失败时节点进入失败状态，以便工作流不会错误地被批准或完成。
13. 作为需要人工接管的成员，我希望 `blocked` 继续表示可恢复的阻塞状态，以便我可以进入 session、处理问题并恢复执行。
14. 作为需要排查故障的成员，我希望 `failed` 显示为“失败”而不是“阻塞”，以便我能快速选择正确的处理动作。
15. 作为需要排查故障的成员，我希望在执行视图和节点详情中看到一致的失败状态，以免不同页面表达冲突。
16. 作为需要排查故障的成员，我希望错误信息来自真实 task 错误，而不是被塞进正常输出，以便输出、错误和交付物的语义保持清晰。
17. 作为工作区成员，我希望所有运行时提供者产生的 `failed` 节点都使用相同展示语义，以便产品行为不依赖具体提供者。
18. 作为桌面端用户，我希望后端升级后旧版本仍能安全显示工作流，以便新增失败展示不会造成白屏或无法打开执行视图。
19. 作为 Web 用户，我希望节点状态变化通过现有实时更新链路出现，以便不需要手动刷新页面。
20. 作为数智人运行时维护者，我希望日志能区分内部重试、终态失败和用户取消，以便快速定位错误发生在哪一层。
21. 作为 cs-cloud 维护者，我希望 session 完成判断有明确的单一终态规则，以便未来新增 CSC 错误 subtype 时默认安全失败。
22. 作为 CSC 维护者，我希望下游使用已有的 session 事件契约，以便不需要为 Multica 增加专用事件。
23. 作为 Multica 维护者，我希望复用现有 task 失败状态机，以便节点失败、工作流失败、通知和实时事件继续保持一致。
24. 作为 Multica 维护者，我希望完整错误消息与粗粒度 `failure_reason` 分开保存，以便重试策略不依赖不稳定的错误文本。
25. 作为测试维护者，我希望成功、重试、失败和取消通过协议边界测试覆盖，以便实现重构不会重新引入“错误显示完成”的问题。

## Implementation Decisions

- CSC 继续作为 session 执行结果的事实来源。现有 `session.result`、`session.error`、`session.status` 和 `session.idle` 事件足以表达本功能，默认不修改 CSC 协议。
- cs-cloud 的 CSC session 等待逻辑必须先观察到当前 prompt 进入 `busy`，再接受对应的终态，继续避免历史或抢跑的 `idle` 事件提前结束新执行。
- `session.result` 是终态成功或失败的权威信号。满足以下任一条件即为失败：
  - 结果的错误标记为 `true`；
  - 结果 subtype 存在且不是 `success`。
- cs-cloud 在协议边界兼容当前使用的 camelCase 错误标记，并可防御性接受等价的 snake_case 标记。未知的非成功 subtype 按失败处理，避免未来新增错误类型时误报完成。
- `session.error` 用于补充用户可读错误信息，不因任意一条 `session.error` 立即结束执行。`api_retry` 是中间态通知，必须等待最终结果。
- 工具 part 的错误状态不等同于 session 失败。只要 CSC 最终结果成功，task 仍然完成。
- 终态结果可能先于对应的 `session.error` 到达。cs-cloud 应当记录终态判定，并等到当前执行的 idle 边界再返回，以便收集紧随结果到达的错误详情。
- 错误消息按以下优先级生成：
  1. 对应终态 `session.error` 中的用户可读 message；
  2. 终态结果携带的首个用户可读错误；
  3. 终态 subtype 的稳定描述；
  4. 通用的 CSC session 执行失败消息。
- 不向 Multica 透传完整原始事件、认证信息或内部堆栈。上报内容是经过解析的用户可读错误消息。
- CSC 终态失败必须让 session runner 返回非空错误。workflow driver 看到该错误后调用现有 task 失败接口，不得继续调用 task 完成接口。
- cs-cloud 向 Multica 上报 CSC 终态失败时使用 `failure_reason = agent_error`。完整错误消息放入 task 的 `error` 字段，粗粒度原因继续只用于重试分类和 UI 标签。
- CSC 自己负责 `api_retry`。一旦 CSC 给出最终失败结果，Multica 不再自动重试该 task；用户可以使用现有节点手动重试动作。
- 用户通过现有终止流程取消 task 时，cs-cloud 保持取消语义，并使用取消分类上报，不将其转换为普通 `agent_error`。
- Multica 继续使用已有的 `node_run.status = failed`，不增加新的 `error` 节点状态，也不修改 `blocked` 的含义。
- `blocked` 表示可以人工介入、恢复、跳过或完成的阻塞状态；`failed` 表示本次节点执行已经错误终止。两者在状态机和用户界面中都必须保持独立。
- Multica 现有 task 失败处理继续负责把关联的 worker 或审核 task 失败传播到节点，并由节点失败触发工作流终态检查。
- 节点错误详情从关联 `agent_task.error` 投影到已有的节点运行摘要 `error_message`。应批量读取当前工作流运行关联的 task 错误，避免逐节点查询。
- 错误投影根据当前失败阶段选择对应 task：worker 阶段优先 worker task，审核阶段优先审核 task；仅在缺少阶段专用关联时才使用通用 agent task。
- 不把错误消息写入 `worker_output`、`critic_output` 或节点的粗粒度 `failure_reason`。这些字段继续分别表示正常执行输出、审核输出和状态机级原因。
- 不需要新增数据库列或迁移。task 已有完整错误字段，节点摘要已有 `has_error` 和 `error_message`。
- Multica 共享执行视图根据节点的精确 `failed` 状态显示“失败”，并使用错误视觉样式；精确 `blocked` 状态继续显示“阻塞”。
- “失败”展示对所有运行时提供者生效，不增加 `provider == cs-cloud` 或 `agent == csc` 的前端特判。
- Web 和桌面端共用的状态映射、图标、状态标签和节点详情逻辑放在共享包中，不复制平台实现。
- 为保护已安装桌面端的 API 兼容性，不要求通过新增服务端枚举值才能区分失败。服务端已经返回精确的 node run 状态；新客户端使用该状态区分 `failed` 和 `blocked`，旧客户端可以继续按已有聚合状态降级显示。
- 节点详情优先展示运行摘要中的 `error_message`，并保留从历史输出读取错误的兼容兜底，以便旧数据仍可查看。
- 继续使用现有 task 失败、工作流节点状态变化和查询失效机制更新界面，不新增 WebSocket 事件类型。

## Testing Decisions

- 测试以协议边界和用户可观察行为为主，不断言私有状态字段、辅助函数调用次数或具体错误解析实现。
- cs-cloud 的 CSC session 接缝使用完整事件序列测试，而不是单独伪造最终返回值。至少覆盖：
  - `busy`、成功 result、`idle` 产生成功；
  - `busy`、`api_retry`、成功 result、`idle` 产生成功；
  - `busy`、非成功 subtype、终态 error、`idle` 产生包含消息的错误；
  - subtype 为 `success` 但错误标记为 `true` 时产生失败；
  - 工具 part 错误后最终 result 成功时产生成功；
  - 历史 `idle` 在 `busy` 之前不会结束当前执行；
  - context 取消仍返回取消错误。
- 上述测试沿用现有 CSC agent session 等待测试接缝，并将断言提升到 session runner 的外部返回结果；只有难以稳定构造 HTTP/SSE 时，才在事件状态机边界补充更小的单元测试。
- cs-cloud workflow driver 使用现有模拟 Multica 服务测试：
  - session runner 返回终态错误时只调用 `/fail`；
  - 失败请求包含用户可读错误和 `agent_error`；
  - 同一执行不调用 `/complete`；
  - session runner 成功时仍只调用 `/complete`；
  - 用户取消使用取消分类。
- Multica 后端沿用已有工作流失败集成测试接缝，从 task 失败入口验证：
  - 关联 task 保存完整错误；
  - worker 或审核节点进入 `failed`；
  - 工作流按现有规则进入失败终态；
  - 节点运行摘要返回 `has_error = true` 和 task 的错误消息；
  - `blocked` 节点不会被错误标记为 `failed`。
- Multica 后端错误摘要测试应覆盖批量工作流节点，确保成功节点没有错误、失败节点读取正确阶段的 task 错误，并防止 worker 与审核错误串位。
- Multica 共享前端沿用节点状态映射、状态图标、运行节点卡片和节点详情组件的现有测试接缝，验证：
  - `failed` 显示“失败”和错误样式；
  - `blocked` 继续显示“阻塞”；
  - 失败节点详情显示运行摘要中的错误消息；
  - 成功节点不显示陈旧错误；
  - Web 与桌面端共享相同行为。
- API 响应解析测试应包含缺失或未知错误字段，确保错误详情缺失时仍能显示失败状态，而不会导致界面崩溃。
- 不新增跨仓库 E2E 测试框架。三个仓库独立发布，测试分别锁定 CSC 事件消费、cs-cloud 回调和 Multica 展示三个稳定协议接缝。

## Out of Scope

- 修改 CSC 的重试算法、最大重试次数或 provider 错误分类。
- 为 Multica 增加专用 CSC 错误事件或专用 cs-cloud 节点类型。
- 将单次工具调用错误直接升级为节点失败。
- 对 `agent_error` 增加 Multica 自动重试。
- 新增 `error` 节点状态、数据库枚举或数据库错误列。
- 改变 `blocked` 的人工接管、恢复、跳过或手动完成能力。
- 将完整 CSC 原始事件、provider 响应体或堆栈长期保存到 Multica。
- 重构所有工作流状态或重新设计节点运行摘要 API。
- 建立覆盖 CSC、cs-cloud 和 Multica 三个仓库的统一部署级 E2E 环境。
- 改变与本问题无关的工作流格式校验失败、审核驳回或 split 节点状态语义。

## Further Notes

- 当前根因位于 cs-cloud 的 session 完成判断：它只把 `busy → idle` 当作完成，没有读取此前已经到达的终态结果。
- CSC 当前事件顺序会在 idle 之前发送 result，并可能在 result 之后发送补充 error。因此实现需要在 idle 边界统一裁决，而不是收到第一条 error 时立即返回。
- Multica 的 task 失败到节点失败链路已经存在。只要 cs-cloud 调用失败接口而不是完成接口，节点状态机即可进入正确终态。
- 当前 Multica 节点错误摘要主要从正常输出解析错误，这不适用于 CSC session runner 返回错误、没有正常输出的场景。task 的 `error` 字段是该信息的正确来源。
- 实现预计涉及 cs-cloud 和 Multica。除非验证发现现有事件缺少必要信息，否则 CSC 不需要代码改动。
- 发布顺序建议先发布能够正确消费 CSC 终态的 cs-cloud，再发布区分 `failed` 与 `blocked` 并展示 task 错误的 Multica。任一侧单独发布都应保持安全降级：新版 cs-cloud 对旧 Multica 仍使用既有失败接口；新版 Multica 对旧 cs-cloud 仍按收到的完成或失败回调工作。
